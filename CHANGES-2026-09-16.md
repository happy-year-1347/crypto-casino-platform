## 2. Crypto cashier (NOWPayments)

Full deposit and withdrawal flow for BTC, LTC, USDT (TRC20 / ERC20), TRX, DOGE,
plus ETH, USDC and BNB if you enable them. See `CRYPTO_SETUP_GUIDE.md` for the
developer map and `deploy/DEPLOYMENT.md` section 8 for the operator setup.

Player side
- Deposit page: coin picker (only coins enabled in your NOWPayments account),
  amount in the site currency, **live conversion rate**, provider minimum check,
  pay address + QR + memo, expiry countdown, automatic status polling and instant
  balance credit.
- Withdraw page: coin + destination address, live estimate of coins to receive,
  address validation, per-player withdrawal limits.
- Transactions page shows crypto deposits / withdrawals like any other.

Admin side
- **Financial > Payment Gateway**: enable, sandbox toggle, API key, IPN secret,
  callback URLs to paste into NOWPayments, coin list, fee option, payout login,
  **Test connection** button.
- **Financial > Withdrawals**: coin, address, payout status, tx hash columns and a
  *Crypto payout* menu per pending request: Send via NOWPayments (2FA), Confirm
  2FA, Refresh, Mark paid manually, Cancel & refund.
- **Financial > Deposits**: coin, crypto amount, provider status, *Check provider*
  and *Credit manually* (for partial payments).

Security / correctness
- Every IPN is verified with HMAC-SHA512 against the IPN secret (the previous code
  accepted any POST and would have credited balances to anyone).
- Deposits are credited once, replayed callbacks are ignored.
- Crypto deposits go through the same crediting as PIX did: welcome bonus, bonus
  rollover, deposit rollover, VIP points, affiliate CPA, admin notification.
- Withdrawal cancel now refunds correctly (the old code looked up the wallet by
  the coin code and silently failed).
- Withdrawal limits are per player instead of platform-wide, and canceled
  requests no longer count.
- The NOWPayments account password is stored encrypted.
- The old `CryptoTrait` was removed; `PIX`/SuitPay and Stripe code is untouched
  and stays disabled.

## 3. Security fixes found during the review

- **Removed a file-upload backdoor**: `public/js/filament/support/index.php`
  let anyone upload a PHP file into the web root. Also removed stray PHP files
  inside `public/originals/*` (old standalone game APIs and a leftover routes
  file), `public/logs.txt` (old provider log with tokens), `composer.phar`,
  `composer-setup.php` and the one-off `create_admin.php` / `create_user.php` /
  `setup_admin_role.php` / `enable_crypto.php` scripts (they created a known
  admin password `admin123456`).
- **Game session tokens are now signed** (HMAC with APP_KEY). Before, the token
  was a reversible substitution cipher of `{"id": <user>, "game": ...}`, so a
  player could craft a token for another user id and spin with that user's
  balance. Forged tokens now get HTTP 401. `MakeToken`/`DecToken` in
  `app/Helpers/Core.php`.
- `/api/vgames/{token}/{action}` returns proper 401/404 instead of an empty 200.
- `/clear` (cache clear) now requires an admin login; the unauthenticated
  `/test` provider route was removed.
- Root `.htaccess` no longer enables directory listing.
- Production `.env` template ships with `APP_DEBUG=false`, no third-party keys,
  and a note to generate new APP_KEY / JWT_SECRET (the shipped `.env` contains a
  Google OAuth secret and a mailtrap login that should be rotated).

## 4. Gameplay fixes for the 12 local slots

- Every spin now writes a row to `orders` (bet -> win/loss), the same convention
  as the API providers, so the player's Records page, Recents, profile stats and
  the admin "My bets" widget work for these games. Previously the local games
  wrote no history at all.
- The win/loss history call passed the wrong arguments (game name where the
  balance type belonged), which skipped affiliate revshare on losses and
  mis-routed the win rollover. Fixed.
- `total_bet`, `total_won`, `total_lose`, `last_won`, `last_lose` on the wallet
  are updated.
- A bet larger than any single balance bucket is now taken across bonus ->
  deposit -> withdrawable balance instead of being silently ignored.
- Free-spin endpoint no longer fatals (signature mismatch with the controllers).
- Guard rails: invalid game / wallet / empty result table return 400 instead of
  a 500.

## 7d. End-to-end bug sweep (2026-09-17)

Found by reviewing every money path, every admin page and every leftover in the
original package.

- **Two players' worth of money could be spent once.** The withdrawal request,
  the affiliate commission withdrawal and the game spin all read the balance,
  then wrote it, without locking. Two requests arriving together both passed the
  check. Proven locally: six simultaneous spins of 60 on a balance of 100 all
  went through (300 bet from 100). Now the wallet row is locked while it is
  checked and debited, so only what the player actually has can be spent.
  (`WalletController`, `AffiliateController`, `PrivateGamesTrait`.)
- **A withdrawal could be refunded twice**: a cancel and a "payout failed"
  callback arriving together both refunded. The status is now claimed atomically,
  and the second one is ignored. (`CryptoPayoutService`.)
- **Any player could activate another player's wallet**: `setWalletActive` took
  any wallet id. It is now limited to the player's own wallets.
- **A mission could be accepted many times**, and each row could pay its bonus.
  One row per player and mission now, and the mission id must exist. The endpoint
  also returned empty messages; it returns real ones now.
- **`php artisan route:cache` crashed**, so the site ran without a route cache
  (slower on every request). The package's RoleResource had been copied into
  `app/Filament/Resources` under the package's own namespace, so the class was
  declared twice. Removed; the same restriction (admins only) is now a policy
  (`app/Policies/RolePolicy.php`, `PermissionPolicy.php`). `deploy.sh` caches
  routes and events again.
- **Debug leftovers removed**: `dd("dsfsdsdf")` in the admin games page and eight
  `dd()` calls in provider code, which would have dumped internals and killed the
  request if reached.
- Mission rewards no longer fatal when a player has no active wallet.

Found while going live on the new server:

- **The route cache silently dropped the whole player site.** `routes/web.php`
  and `routes/api.php` pulled their groups in with `include_once`. When
  `route:cache` builds, the route files are loaded a second time in the same
  process, so every `include_once` was skipped and only the admin routes were
  cached: the live site answered 404 on `/`, `/api/...` and every player page.
  Changed to `require` (157 routes cached, same as uncached).
- The settings API did not return `software_favicon`, so the mobile header
  requested `/storage/undefined` (a broken image on every phone visit).
- Unknown multi-segment URLs rendered a blank page; the Vue router now sends
  anything unknown to the home page.

Found in the password reset flow (2026-09-18):

- **Anyone could take over any account.** The reset token was checked on its own,
  not against the e-mail address, and never expired: a player could ask for their
  own link and use that token to set a new password on somebody else's account.
  The token was also only 5 characters. Now it is 40 characters, must belong to
  that e-mail, and expires after an hour.
- With no mail server configured, "Forgot password" threw a 500. It now answers
  with a readable message in the player's language and leaves no dead token.
- Admin pages that write to `.env` (Mail, Settings, Default) never refreshed the
  cached config, so on a production server those saves looked like they did
  nothing. They rebuild the cache now, which is what makes the SMTP page usable.

Found while the site was already live (2026-09-18):

- **Nothing was rate limited.** The API limiter existed in the code but was never
  added to the middleware group, so login, registration and password reset
  accepted unlimited attempts. Those endpoints now allow 10 tries a minute per IP
  and 5 per e-mail address; everything else 300 a minute, which leaves fast
  players and shared mobile IPs alone (40 spins in a row still pass).
- **Game session tokens never expired.** The game opens in an iframe with the
  token in the URL, so it can survive in browser history or a screenshot. Tokens
  now carry a signed expiry of 24 hours.
- **The 1.4 MB app bundle was served uncompressed**: nginx only gzips HTML out of
  the box. With compression it leaves the server at 425 KB (stylesheet 115 KB ->
  21 KB), and the hashed build files are cached for a year.

New tests: `tests/mock/password-reset.php`, `tests/mock/rate-limit.ps1`,
`tests/mock/game-token.php`, `tests/mock/concurrency.ps1` (simultaneous withdrawals and spins, run
as parallel processes because `artisan serve` is single threaded),
`tests/mock/roles-access.php` and `tests/mock/route-cache.php` (cached route

## 7f. The RTP field, which was not doing what it says (2026-09-18)

The client asked where he controls how much the twelve slots win and lose. The
answer was **Games > All Games > a game > RTP**, but the field did not behave
like an RTP at all, and the values it shipped with would have cost him money the
day crypto went live.

**What it used to do.** Each spin filled a bag with `rtp` winning results and
`100 - rtp` losing ones and drew one out. With `rtp = 90` and a pool of 14
winning rows, the bag ended up 14 wins to 10 losses, so 58% of spins won. A
winning row pays `payout / num_line` times the stake, and the average winning row
in these games pays 64 on 5 lines, about 13 times the bet. Ten of the twelve
games were set to 90, which works out at **roughly 7.5 back for every 1 staked**.
`tests/mock/rtp-table.php` prints that table from the game data.

**What it does now.** The field is the percentage of the stake the game gives
back over time, which is what the label always claimed. The chance of a winning
spin is the target divided by what an average win pays, so a game with big rare
prizes wins less often and a game with small prizes wins more often, and both
land on the same payback. The demo account is untouched: it still wins nine
spins in ten, and it never touches real money.

**A second bug found on the way.** Queen of Bounty and Treasures of Aztec store
their prize inside the winning-line detail instead of at index 5, where the code
read it. Both games have been paying **zero on every win**: the reels showed a
win and the balance did not move. The payout now falls back to the winning-line
detail, and those two games pay properly.

**Verified** with `tests/mock/rtp-simulate.php`, which runs the real selection
code 400,000 times per game. At a setting of 92 the twelve games paid back 91.9%
on average, every one of them between 90.1% and 95.6%. Win rates ranged from 2%
to 48% depending on how big that game's prizes are, and the largest single win
seen was 814x the stake. Treasures of Aztec and Queen of Bounty sit at the top of
that range because their prizes are rare and huge, so they need far more spins to
settle on the number; the other ten land within a point or two of it quickly.

A run of 400 real spins on the live site afterwards returned 80.6% of the stake,
which is ordinary noise at that sample size: one 50x win either way moves it by
12 points.

All twelve games are now set to 90. Fortune OX was on 2 and Fortune Rabbit on 10,
left over from the package; under the new meaning those would have paid back 2%
and 10%, which is a game nobody plays twice.
